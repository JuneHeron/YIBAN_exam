# 油猴脚本 · 题库桥接版

把页面上渲染出来的题目发给本地题库取答案；题库里没有的随机选。全手动触发，没有自动流程。

## 为什么需要一个本地服务

油猴脚本跑在浏览器里，**读不到本地 SQLite**。所以由 `bank.py` 提供一个只监听本机的
桥接服务，脚本通过它查询和入库：

```
浏览器（油猴脚本）  --HTTP-->  127.0.0.1:8765（bank.py serve）  -->  bank.db
```

这样就复用了已有的全部逻辑——尤其是**按选项原文反查字母**。
平台每次打乱选项，脚本把「题干 + 当前页面上的选项顺序」发过去，服务端返回**对应这个顺序**的
字母，所以打乱也不会答错。

## 启动（给使用者看的最短流程）

1. 装 Python（一次性）：<https://www.python.org/downloads/>，安装时勾选 `Add python.exe to PATH`
2. **双击 `start.bat`** —— 黑窗口别关，它就是服务；浏览器会自动打开说明页
3. 说明页上点链接装脚本（油猴会弹安装页）→ 打开考试页面，右下角出现面板

手动方式的等价命令（排查问题时用）：

```bash
python bank.py serve          # 起服务
python bank.py serve --open   # 起服务并自动开说明页
python bank.py serve --port 8766   # 端口被占用时换一个
```

面板显示「未连接」就是服务没在跑。脚本也可以通过
`http://127.0.0.1:8765/yiban-bank.user.js` 安装——服务会把这个文件发给油猴。

## 面板上的东西

| 控件 | 作用 |
| --- | --- |
| **自动答题** | 从第一题开始，逐题查库、点选项、**自动点「下一题」**，一路答到底。**不自动交卷** |
| **采集入库** | 在**交卷后的试卷页**用。同样遍历整份卷子，把每道题的「题目 + 正确答案」收起来一次性入库 |
| **诊断** | 把识别到的题干、选项、读到的答案打到控制台（F12） |
| **快速模式** | 勾上走**两遍批量**路径：先只读收集 → 一次问完 → 再一遍点选。看不见翻页，速度接近参考脚本。不勾则逐题边走边问（慢、像人在点） |
| **清空题库** | 见下 |

自动答题和采集共用一份遍历逻辑（`forEachQuestion`），都会**先退回第一题**再开始，否则从半路
只会答剩下的几道。停止条件：页面没题、下一题按钮消失或禁用、进度到末尾、翻页后题干没变。

## 为什么快速模式要「两遍走」

答题原来比采集慢、而且**看得见翻页**，原因只有一个：**每道题都要问一次本地服务**。
服务本身很快（一次往返约 20ms），但**每次请求的 `await` 都会让浏览器有机会重绘**——
100 道题就是 100 次重绘机会，所以翻页看得见。采集入库之所以快，正是因为它全程不发请求。

所以快速模式改成：

1. **第一遍只读不点**：逐页收集「题干 + 选项」，期间不发任何请求
2. **一次**批量问本地库（`/ask-batch`），拿到全部答案
3. 回到第一题
4. **第二遍逐页点选**：答案已在手，循环里没有任何网络等待

两遍内部都不等待，浏览器来不及在题目之间重绘。实测 3 次单条请求 69ms → 1 次批量 10ms。

两遍之间**按题干对应答案，不按下标**。万一某遍遍历因停止条件不一致而错位，
按下标会把答案点到别的题上（实测演示过：第一遍漏收中间一道，则后面全体错位），
按题干取不到就走随机，绝不会点错。

慢速模式仍是逐题边走边问的老路——慢，但过程像人在点。

### 另一处更大的开销：翻页后的探测间隔

「点下一题 → 等题干变」这个等待原来是**每 100ms 探一次**。只要 React 的更新晚一帧
（16ms），第一探就落空、白等整整 100ms。算一下：

| DOM 更新延迟 | 100ms 探测 → 每题多等 | 20ms 探测 → 每题多等 |
| --- | --- | --- |
| 16ms | 100ms（100 题 10 秒） | 20ms（100 题 2 秒） |
| 33ms | 100ms（100 题 10 秒） | 40ms（100 题 4 秒） |

实测答题 125~148ms/题、采集 125ms/题，正好落在这个量级上——**两个操作都卡在同一个等待里**，
这也是采集看起来快、答题看起来慢之外的另一半原因。现在改成：

- 探测间隔 **20ms**（快速模式下）
- 判据**优先看进度计数器**（读一个数字），读不到才退回「整页扫 DOM 比题干」（贵得多）

## 清空题库

面板上的「清空题库」→ 先让你填范围（`script` 只清脚本采集的 / `all` 全清）→ 再 confirm 一次。
**服务端在删之前一定自动备份**，返回里会带备份文件名，点错也能还原：

```bash
python bank.py clear             # 预览：列出各来源有多少题
python bank.py clear --all --yes # 真删（删前自动备份）
```

## 已知的页面结构（从 F12 拿到，都进了自动化验证）

```html
<div class="jsx-3643416060">题干的文字</div>            <!-- 题干单独一个 div -->
<button>冲！</button><button>随机选择</button>            <!-- 另一个脚本注入的，与题干平级 -->
```

要点：

1. **题干单独在 div 里，注入的按钮与它平级**。所以「取容器整段文本」必然把按钮文字吃进题干。
   已改成按结构取：容器内最内层文本块，排除选项、`button` 和自己的面板（`extraText()`）。
2. **class 是 React 构建哈希**（`jsx-3643416060` 这种），换个版本就变，所以一律不按 class 找。
3. **选项选中态藏在图标 svg 的路径数里**：选中 2 个 `<path>`（外圈+对勾），未选中 1 个。
   有了它，多选题才能「只在状态不对时才点」，而不是靠猜点几次。
4. 选项文字元素点一下即可：click 会冒泡到 `li`，处理函数挂整行或挂文字都能触发。

## 已验证 / 未验证

**已验证：**

- 桥接服务三个接口（`/ask` `/learn` `/clear`）全部实测通过
- `/ask` 的选项重排：同一题原顺序返回 D、打乱后返回 A，都对
- 结构识别算法：用 Python 等价实现喂两份**真实 DOM 副本**（试卷页单选、答题页多选），
  题干、选项、容器、正确答案全部正确 → `check_algorithm.py`
- 脚本结构：字符串完整性 + 括号配平 → `check_balance.py`

**未验证：**

- **没有在浏览器里跑过**。本地没有 node/deno（代理不通也装不了 esprima），
  所以 JS 只做了机械检查。真正的验证是在浏览器里加载一次，看控制台有没有报错。
- 平台的 DOM 我只见过四个页面（试卷页、答题页、成绩页、列表页、考试信息页），
  其它页面若有则需要再调。

## 已知风险

- **平台可能检测脚本**，不保证。非快速模式下每题之间有等待，过程看得见。
- **人机验证是答题前的准入环节**，跟答题快慢无关，每进一次考试都要过——那一步得人来。
  参考脚本里过验证码的代码（把验证码图片 URL 发给一个第三方服务器换点击坐标）**没有接进来**：
  那不是一段代码而是一个外部依赖，它本身就不稳（那份脚本专门写了「无法连接服务器」的兜底界面），
  接进来等于把验证码图片交给陌生第三方，还可能在中途超时。性价比不划算。
- 桥接服务只绑 `127.0.0.1`，外网访问不到，但也别在公共网络下开着不管。
